# Parola system and reliability audit

Snapshot: `main` at `bd60180cc4eea7d9c0bd45e41584048ec752fba1`, inspected 3 October 2026. Read-only source review plus focused isolated tests. This covers persistence, backup and sync, offline/PWA/build/deploy, optional local AI, scaling, and shared accessibility infrastructure. It does not re-report the 1 October findings that were fixed: the README is updated, deploy now gates on the shared browser matrix, a dedicated `dist/` excludes docs/tests, and the service worker stamp is content-derived.

## Priority findings

### P1 — Save failure is silent and success can be false

`kvSet()` returns `false` on IndexedDB transaction failure; the localStorage fallback's `localSet()` also returns `false` on quota failure (`js/store.js:32-52,66-79`). `saveNow()` sets `_dirty` and emits `saveError`, but resolves its promise either way (`js/store.js:310-337`). No application listener for `saveError` exists. `importJSON()` awaits that resolving promise (`js/store.js:650-652`), and the profile view then displays “Backup imported” (`js/views/profile.js:263-274`). `resetProgress()` and create/switch similarly do not surface a failed commit (`js/store.js:276-282,654-660`; `js/views/profile.js:243-244`).

Reproduced in an isolated clean-HEAD Node harness: after forcing `QuotaExceededError` for profile writes, replace-import resolved, `_dirty` remained `true`, and the persisted profile retained the old name while the in-memory profile carried the new one. A reload in this fallback state restores the old copy. Recommendation: make save operations return/throw a durable result, fail import/reset success messaging when the commit fails, and display a persistent save warning with a backup action for ordinary edits. This matters more as evidence histories grow.

### P1 — Optional assistant remains resident after leaving the workshop

Enabling the assistant loads a WebLLM GPU engine; its own documentation says the loaded engine uses about a gigabyte and `releaseAssistant()` is intended when leaving a lesson (`js/learning/assistant.js:138-160,176-185`; `docs/ASSISTANT-EXPERIMENT.md:16,33,37`). Workshop enable invokes `enableAssistant()` (`js/views/labFrasi.js:118-126`), and the lesson may invoke it lazily (`js/views/labFrasiLesson.js:251-268`). Neither view's cleanup invokes `releaseAssistant()` (`js/views/labFrasi.js:139`; `js/views/labFrasiLesson.js:451-459`). A source-wide search found no application call to `releaseAssistant()` at all. Thus an opt-in load can remain in memory across navigation until a manual disable, page unload, or failure; this defeats the mobile memory guard. Recommendation: release on exit from the workshop/lesson and profile changes, then reload from cache on the next need. Verify on the intended physical phone; automated checks use a fake runtime and do not measure memory.

### P1/P2 — A cloud account can merge two distinct local learners

Local profiles are separated by ID (`js/store.js:205-225,259-282`), and sync settings are per local profile (`js/sync.js:5,9-14`). The Supabase schema has exactly one row per auth user (`js/sync.js:130-135`); `pull()` selects by `user_id` only (`js/sync.js:72-75`), then `syncNow()` merges that row into the active profile (`js/sync.js:86-97`). `importJSON(...,{merge:true})` does not compare remote and local learner identities (`js/store.js:615-643`). If two local learners sign in to the same Supabase account, their evidence, lists, custom words, and workshop sentences merge. The UI says “Keep this user's progress in sync” but does not warn that one account represents one learner (`js/views/profile.js:281-293`). Recommendation: bind and display a remote learner identity and stop a mismatched merge, or explicitly require one account per learner and enforce it at sign-in. This is a cross-profile isolation risk; no live Supabase account was used.

### P2 — List deletion and item removal are undone by stale merge

The merge creates any remote list missing locally and unions items for existing lists (`js/store.js:629`), while `deleteList()` and `removeFromList()` simply remove local state (`js/store.js:522-524`). There is no list or membership tombstone. Reproduced with a stale backup: create a list, add an item, export, delete the list/item, then merge the export; both return. Automatic sync uses the same merge path (`js/sync.js:90`). Custom-word deletion already has tombstones (`js/store.js:537-547,631-637`), a good pattern to extend to lists and memberships. If removal means “forget this,” the current behavior is misleading.

### P2 — Independent workshop completions lose XP on merge

A sentence-workshop completion records a timestamp under `lab.frasi.done` and awards 15 legacy XP (`js/store.js:106-142,587-595`). Lab merge unions distinct completed lessons, but the generic legacy-XP merge takes the maximum of device totals, and a same-day `stats.days` record is copied only if absent (`js/store.js:619-643`). Reproduced from a shared zero-XP snapshot: device A completes lesson A, device B completes lesson B; after merge both lessons show done, but total XP and today's XP are 15 instead of 30. Recommendation: represent completion awards by stable IDs and derive/deduplicate XP from those records; reconcile daily counters from mergeable events rather than copying one device's day wholesale.

### P2 — Assistant offline and privacy guarantees are weaker than the UI states

The assistant imports executable runtime code from `https://esm.run/@mlc-ai/web-llm@0.2.85` on each load (`js/learning/assistant.js:12,121,147`). The service worker handles only same-origin fetches (`sw.js:91-107`) and preserves WebLLM's model caches, not that cross-origin runtime. If the browser HTTP cache lacks the runtime on an offline reopen, cached weights do not suffice; the module catches load failure and turns itself off (`js/learning/assistant.js:149-153`). The docs/UI say it works offline after download and that no learner text leaves the device (`docs/ASSISTANT-EXPERIMENT.md:19,57-59`; `js/views/labFrasi.js:64`). Wrapper code sends no learner text over the network, but third-party runtime code executes with page privileges, so the absolute privacy statement is not verifiable from this repository alone. Recommendation: serve a pinned runtime from the app origin, include it in the offline contract, audit actual network requests, and describe the guarantee as tested. No exfiltration was observed or claimed here.

### P2 — All courses sit on the startup critical path

`boot()` starts the dictionary and `loadGrammarCourse()` in parallel, but awaits both before rendering the first screen and then attaches lesson vocabulary across all current lessons (`js/app.js:201-221`). `loadGrammarCourse()` fetches 7 new and 6 legacy level packs in one `Promise.all`; one failed pack rejects the whole course load (`js/learning/grammar-course.js:24-45`). The service worker precaches 132 files, 9.87 MiB raw at this HEAD (`sw.js:18-44`); its atomic install gives consistent offline content, but a transient failure of any resource leaves no new offline shell. The app ignores service-worker registration failure (`js/app.js:228-235`). Recommendation: measure cold-start on a midrange phone, then load only the active level and a compact index on the critical path while preserving per-level offline readiness and progress migrations. Give the learner an offline-ready/error state. This is an architectural load and failure-coupling finding; no speed regression number is asserted.

### P2/P3 — Long-lived event histories lack a size strategy

Every learning attempt appends an event (`js/learning/model.js:236-245`); state replay normalizes and sorts the full event collection when the reference changes (`js/learning/model.js:392-410`). Every save serializes the whole profile (`js/store.js:310-337`), and every cloud sync uploads the whole profile JSON (`js/sync.js:86-99`). `docs/ADAPTIVE-LEARNING-RELEASE.md:35` acknowledges compaction is future work. This preserves an excellent audit trail and deterministic merges, but cost grows with total lifetime answers and can hit the small localStorage fallback quota. Recommendation: benchmark representative 1k/10k/50k-event profiles on phone hardware and define acknowledged compaction or per-record IndexedDB storage before growth becomes a learner-facing problem.

### P3 — Backup scope and small accessibility/release details

- “Export backup” serializes the profile only (`js/store.js:609`; `js/views/profile.js:223-227`). Course microphone recordings live in a separate IndexedDB (`js/learning/course-v2-media.js:27-49`) and are not in this JSON. The lesson correctly says to export recordings separately (`js/views/learnCourse.js:203-205`); the profile backup UI should state that limitation before a device move.
- `index.html:5` sets `maximum-scale=1`, which can block or constrain mobile pinch zoom. Remove it and verify the keyboard/viewport code, which already handles zoomed views specially (`js/ui.js:12-21`). Other shared accessibility work is in the UX audit.
- The fit-scorer row says “70 MB download” (`js/views/labFrasi.js:62`), but its declared four assets total 83,251,573 bytes, about 79.4 MiB (`js/learning/fit-scorer.js:21-27`), and the same pane says ~83 MB (`js/views/labFrasi.js:48,113`). Use one consistent unit and figure.
- The on-demand model/cache version is manually named `v1`, and cache hits are accepted by size (`js/learning/fit-scorer.js:15-27,80-99,120-126`; `sw.js:9-12,78-90`). The shell stamp deliberately excludes model/runtime assets (`tools/check-shell.mjs:22-25`), so a future same-size model or runtime change could keep an old cached copy. Use a content hash/manifest or require a checked cache-version bump for optional assets. This is a future release hazard, not a current mismatch.

## Strengths and confirmed fixes

- The deploy graph builds a clean `dist/` and gates publishing on deterministic checks and 20 Playwright suites (`.github/workflows/deploy.yml:17-20,32-96`; `.github/workflows/browser.yml:13-42`). This closes the previous direct-push browser gap. The build excludes authoring sources, docs, tests, tools and scratch files (`tools/build-site.mjs:19-27,31-69`), closing the earlier whole-repo artifact problem.
- The current SW stamp matches its shell, and install waits until the complete shell is cached (`tools/stamp-sw.mjs:67-98`; `sw.js:39-46`). Downloaded audio and the fit scorer have separate caches; 66 MB of model weights and 14 MB runtime are on demand (`sw.js:8-17,64-90`; `js/learning/fit-scorer.js:6-27`). The built site is 280 files / 102.57 MiB, while the 132-file shell is 9.87 MiB raw; the full artifact size is not the first-install transfer.
- Revision-checked Supabase writes refetch and merge on conflict, rather than blind overwrite (`js/sync.js:78-113,156-175`). Learning events are identified and deduplicated, resets use epochs, and custom deletions have tombstones (`js/learning/model.js:115-150,201-245`; `js/store.js:537-547,631-637`). The focused tests exercise these contracts.
- Optional model advice cannot change an answer grade, and the assistant picks only an index among authored replies (`js/learning/fit-scorer.js:1-4`; `js/learning/assistant.js:4-10,194-282`; `js/views/labFrasiLesson.js:251-279,306-321`). Both can fail without breaking the workshop's deterministic path.
