# Bounded native Apple prototype investigation

The explicitly authorized investigation built and installed a separate native UIKit app, `local.parola.nativeinvestigation`, in the approved iPhone 16 Pro Max / iOS26.5 simulator on the M1 Max32GB Mac. It does not replace the shipped browser app, touch learner profiles, change Apple Intelligence settings, install Apple model assets or call cloud services. Xcode26.6 build17F113 and the iOS26.5 SDK compiled the FoundationModels, Speech and AVFoundation paths; the app has a real editable Italian input and enables local generation only after an actual runtime smoke succeeds.

The simulator advertises FoundationModels availability and Italian locale support. Nevertheless, all 26 frozen generation requests returned errors before producing Italian text. Each error chain includes `FoundationModels.LanguageModelSession.GenerationError`, `SensitiveContentAnalysisML` code15 and `ModelManagerServices.ModelManagerError` code1026. [The first complete report](ai-native-simulator-before.json) preserves every attempted case/error. Its original `generatedResponses:26` field counted attempts, not successful generations; the explicit rows show `ok:false` throughout. The corrected prototype counts successful outputs separately. A later plain 64-token smoke request, without structured generation, fails with the same error chain in 3.21seconds. [The smoke report](ai-native-simulator-after.json) therefore leaves the larger screen skipped and its Send button disabled. This is a simulator/runtime prerequisite failure; there are zero outputs to grade and no evidence that the Apple model teaches Italian incorrectly or fails on a real iPhone.

That result complements the earlier physical Mac probe, whose availability was `appleIntelligenceNotEnabled`. The simulator’s reported availability is different; neither reported availability nor supported-language metadata substitutes for successful inference. Apple’s [FoundationModels availability guidance](https://developer.apple.com/documentation/foundationmodels/generating-content-and-performing-tasks-with-foundation-models) describes the dependency on an eligible device/region and the system model becoming available after Apple Intelligence is enabled. This investigation changed none of those settings. The system-managed model has no immutable weight revision API used here, so OS/build/runtime results must accompany a future quality gate.

Both the new [SpeechTranscriber API](https://developer.apple.com/documentation/speech/speechtranscriber) and the Italian SFSpeechRecognizer reported unavailable in this simulator. SFSpeechRecognizer also reported `supportsOnDeviceRecognition:false`, with authorization still undetermined; no recognition request or permission shortcut was made. These are exact reported states, without a conclusion about physical-device Italian recognition. No installation request was made. The browser transport and injected-adapter work remains independent of those native resources.

Native AVSpeechSynthesizer did provide `com.apple.voice.super-compact.it-IT.Alice`. Its [buffer-writing API](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/write(_:tobuffercallback:)) produced three actual mono Float32 22.05kHz WAV files, retaining the intentional learner auxiliary error as spoken input rather than correcting it. [The measured voice comparison](ai-native-voice-audit.json) pins their SHA-256 and durations. Already provisioned Whisper-base q8 recognised the learner-error and names/context clips with zero normalised word edits. The quantity/negation clip preserved “non”, three versus two and the date, but transcribed `biglietti` as `billetti` and the written number as digits, yielding 2edits/11words. This supports automated text preservation in a tiny synthetic screen; it does not establish native human pronunciation quality, real learner ASR or a speech release.

Source is in `dev/phase-1-ai-trial/native/ItalianPrototype.swift`, with reproducible simulator build/input scripts, the before source revision and exact raw reports retained. Framework code/assets remain Apple system resources under their applicable SDK/system terms; no Apple weights are redistributed. The separate native llama.cpp investigation is the next measured option, using one explicitly approved pinned8B quantised pack and retaining the disk floor. A physical eligible device with a functioning system model remains the concrete way to measure Apple-model Italian quality without assuming the simulator error generalises.
