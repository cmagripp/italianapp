# Offline AI feasibility note — 3 October 2026

Read-only research for the proposed fully offline Italian PWA on the stated iPhone 16 Pro Max / iOS 26.6.1. This is a candidate plan, not a claim of successful inference on that phone. The existing assistant has only fake-runtime guard tests; no physical iPhone or real WebGPU model was exercised in this research.

## Current code and immediate implications

- `js/learning/assistant.js` dynamically imports WebLLM 0.2.85 from `https://esm.run/...`, loads `Qwen3-0.6B-q4f16_1-MLC` at a 1,024-token context, and calls JSON-schema constrained generation for an index into at most 12 authored replies. Its output is never a free generated Italian bubble. It is therefore not yet the requested dynamic tutor. The 6-second pick timeout cannot be assumed suitable for generated conversation.
- `docs/audit-2026-10-03/system.md` confirms the runtime import is cross-origin and outside this app's service-worker offline shell; `releaseAssistant()` is not called by the application views. The advertised “offline after download” claim requires a real cold reopen in airplane mode and a locally served pinned runtime. The selected model should be unloaded when leaving chats and after a profile switch.
- `js/learning/fit-scorer.js` has a separate optional 83 MB cache. Model and scorer caches compete with profile storage on one origin. [WebKit says](https://webkit.org/blog/14403/updates-to-storage-policy/) quota is generous on recent iOS but best-effort storage can be evicted, normally a whole origin; `persist()` and `estimate()` help but cannot promise permanence.

Qwen's own [Qwen3.5 0.8B card](https://huggingface.co/Qwen/Qwen3.5-0.8B) compares non-thinking broad multilingual/English benchmarks: Qwen3.5 0.8B is below Qwen3 1.7B in MMMLU (34.1 versus 46.7) and IFEval (52.1 versus 68.2); Qwen3.5 2B has MMMLU 56.9. These are *not* Italian CEFR, correction, dialogue, or mobile performance results. They argue for a head-to-head trial, not a winner by size. Qwen3's [official announcement](https://qwenlm.github.io/blog/qwen3/) lists Italian among its 119 languages. Qwen3.5's official card advertises multilingualism but contains no Italian tutoring benchmark. Qwen3.5 0.8B and 2B cards describe non-thinking as default; keep it that way to limit latency and rambling.

Other plausible models: [Gemma 4 E2B/E4B](https://ai.google.dev/gemma/docs/core) are newer mobile candidates; Google's 0.84/2.2 GB “mobile text-only” figures are static weights with LiteRT-LM and exclude context/runtime, and there are no WebLLM 0.2.85 prebuilt entries. [ONNX browser exports exist](https://huggingface.co/onnx-community/gemma-4-E2B-it-ONNX), so they are a separate experimental Transformers.js lane rather than native-only. [EuroLLM 1.7B Instruct](https://huggingface.co/utter-project/EuroLLM-1.7B-Instruct) explicitly supports Italian with Apache 2.0 but needs custom browser compilation or a native runtime. [Almawave Velvet 2B](https://huggingface.co/Almawave/Velvet-2B) explicitly targets Italian/English, but its download is gated and no WebLLM prebuilt entry exists; use it as an Italian reference if license/access permit. A generic GGUF/ONNX file cannot be substituted for a WebLLM model ID: [WebLLM requires matching MLC weights and compiled `model_lib`](https://github.com/mlc-ai/web-llm/blob/v0.2.85/README.md). Transformers.js 4.3 [introduced Safari 26+ WebGPU support](https://github.com/huggingface/transformers.js/releases), so ONNX is a separate experimental runtime path, not proof of iPhone feasibility.

## Offline distribution and integrity

- [Safari 26 ships WebGPU](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), and Apple's [WebGPU talk](https://developer.apple.com/videos/play/wwdc2025/236/) advises f16/compression to avoid iOS memory termination. `navigator.gpu` + `shader-f16` is a necessary capability gate but says nothing about available memory or model quality. The catalog's `low_resource_required` label also is not a device certification.
- Downloading assets while online and subsequently running offline is feasible in principle. A normal Home Screen PWA install does **not** embed 447 MB–1 GB of model files or guarantee an HTTP cache. Provision the chosen model **from the installed Home Screen app**, visibly report progress and storage, verify every artifact is cached, and require airplane-mode cold-start generation before marking “Ready offline.” WebKit says Home Screen app storage is separate from Safari's except initial cookie copy: [Safari 17.2 release notes](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/).
- Bundle/pin the executable WebLLM runtime under the site's own origin and make its chunks part of the offline shell. Use a custom model record pinned to an immutable Hugging Face revision and a pinned WebLLM WASM library revision. [WebLLM 0.2.85 supports optional SRI for config, tokenizer and model library](https://raw.githubusercontent.com/mlc-ai/web-llm/v0.2.85/src/integrity.ts), **not parameter shards**; use an app manifest with expected per-shard hashes and verify shards without loading whole large files into JS memory. Test that installed inference makes no network request and does not send learner text.
- [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits) limits a published site to 1 GB with a soft 100 GB/month bandwidth cap. [Regular Git blocks files over 100 MiB](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github), and [Git LFS is unsupported for Pages](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage). The Gemma3 1B and Qwen3.5 0.8B MLC repos contain approximately 151 MB and 127 MB weight shards respectively (from their Hugging Face model file trees), so tracking weights directly in this Pages source is unsuitable. Qwen3 1.7B and Qwen3.5 2B are about 984 MB/1.08 GB *before* the app. Keep weights on an appropriate model/static host for one-time provisioning; keep the app runtime and readiness logic on the site's origin. If the user means offline even before any one-time online model provisioning, a web install cannot meet that without a separately transferred package/large site publication.
- Browser storage is best effort. The installed Home Screen app's exemption from WebKit's seven-day script-storage purge is **not** immunity from storage pressure or user deletion ([WebKit tracking prevention](https://webkit.org/tracking-prevention/), [storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). Preserve/export/sync profile data independently of model assets and provide “repair model” if eviction or a partial download is detected. Automatic app updates must preserve a known-good model cache or revalidate compatibility before switching.

## Native fallback if browser gates fail

The web page has no direct Swift [Foundation Models](https://developer.apple.com/documentation/foundationmodels/) interface. A native iOS app or WKWebView shell with a deliberate [JavaScript bridge](https://developer.apple.com/documentation/webkit/wkscriptmessagehandlerwithreply) can use [SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel), whose on-device model is intended for generated game dialogue and other text; it is available only when Apple Intelligence/device/region/model readiness allows it. Apple's [language guidance](https://developer.apple.com/documentation/foundationmodels/supporting-languages-and-locales-with-foundation-models) explicitly gives Italian instructions and says to test `supportsLocale`. The user's iPhone 16 Pro Max is [Apple Intelligence-compatible](https://support.apple.com/en-lamr/121115), but Apple Intelligence and the required device/Siri language settings must be enabled and the on-device model downloaded. Select the on-device model, not a Private Cloud Compute provider, to keep the requirement offline. Native [MLX Swift examples](https://github.com/ml-explore/mlx-swift-examples/blob/main/Applications/LLMEval/README.md) and [llama.cpp's iPhone sample](https://github.com/ggml-org/llama.cpp/blob/master/examples/llama.swiftui/README.md) are alternative local engines if the system model fails Italian quality or availability. A wrapper will need explicit chat/profile migration because Home Screen PWA data is not automatically shared.

## Physical-phone go/no-go protocol

1. Build a minimal free-generation prototype for **Gemma 3 1B IT, Qwen3.5 0.8B, and existing Qwen3 0.6B baseline**; if stable, challenge them with Qwen3 1.7B and Qwen3.5 2B. Use the same prompt budget and 1–2 short bubbles per assistant turn. Keep the present deterministic workshop as a resilience path, not the free-chat product. Test installed Home Screen app on the exact iPhone/iOS version, with other app state representative of normal use.
2. Record first-download bytes/time and cache usage; first compile; warm load after force close; first-token latency, tokens/s, full-response p50/p95; memory/device loss/reload; battery and temperature. Try 1,024, 2,048, and where stable 4,096 context; do **not** extrapolate catalog 4k VRAM values to a presumed Safari limit. Run a 30–60 minute multi-turn soak and background/resume. Persist a user message before inference and verify no transcript loss if the app is killed.
3. Evaluate 30+ fixed dialogue situations **per CEFR level A1–C2** and an additional correction/word-injection set. Include multi-participant identity, user's name/gender/pronoun preferences, arbitrary words, off-topic turns, typos, mixed English/Italian, code-switching attempts, and prompt-injection attempts to break level constraints. Italian teachers blinded to model score naturalness, grammaticality, CEFR fit, coherence, pedagogical value and false corrections. Broad benchmark scores cannot substitute for this. Keep replayable prompts, seeds/settings, rubric, and model versions.
4. Offline acceptance: provision from the installed app while online, force close, enable airplane mode, reopen three times, continue a saved long chat, trigger a new word and correction, play a local Italian voice/recorded audio, navigate lessons, update app later, and repeat. Inspect network requests on a connected run: none from inference; downloads only in explicit provisioning. Re-check after storage-pressure/low-disk simulation where possible.
5. Decide with predeclared UX gates (proposed targets: no page restarts/ lost turns during the soak; no severe wrong correction or role mix-up; the Italian quality and fully validated reply-latency budgets in section 12 of the combined plan; raw first-token timing is a diagnostic metric, not permission to display unchecked output). These are product acceptance targets, **not measured performance**. If no PWA model meets both language and reliability gates, propose a native iOS path using the system model or a measured local engine for discussion; this changes distribution and requires a product decision. Preserve the PWA's deterministic lessons.

## Speech

`SpeechSynthesisVoice.localService` is defined for local versus remote voices in the [Web Speech API specification](https://webaudio.github.io/web-speech-api/). The current `js/ui.js` prioritizes a stored voice name or familiar Italian voice name before `localService`, may use any Italian voice, and reports success when an utterance is queued. It should select only a local Italian voice for an offline/privacy promise and confirm audible playback in airplane mode on the exact installed app. Availability, user activation and voice quality still require device verification. Existing recorded lesson audio remains the certain offline path when cached. In a native fallback, Apple's [AVSpeechSynthesizer documentation](https://developer.apple.com/documentation/avfoundation/speech-synthesis) states speech generation occurs on device.
