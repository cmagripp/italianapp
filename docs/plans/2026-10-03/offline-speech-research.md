# Offline Italian spoken conversation: runtime research — 3 October 2026

This is a planning and primary-source review, not a phone benchmark. No model weights, app changes, builds or deployments were made. Metadata and source files were read. The target is the stated iPhone 16 Pro Max on iOS 26.6.1, installed Home Screen PWA. None of the ASR+LLM+TTS combinations below has been exercised on that phone. The updated main plan includes written, manually recorded and foreground hands-free conversations, with the same transcripts and study summaries.

## Recommendation and exact initial pipeline

Keep the PWA as the first feasibility lane. Use **microphone PCM → local Silero VAD → multilingual Whisper ASR → visible transcript → the selected local text tutor with existing deterministic validation → verified local Italian TTS**. Prefer this modular pipeline because the transcript remains inspectable and editable and each component can be tested separately. This is a buildable candidate, not proven feasibility. The main plan compares text-tutor and direct-audio alternatives separately.

1. Prepare the selected local Italian voice before enabling **Start spoken conversation**. Its tap establishes microphone permission and the audio session. Make a short, audible Italian welcome/test utterance through that voice synchronously in the real Start handler **before awaiting microphone permission, model loading or another promise**, and resume the app’s AudioContext in that gesture. A microphone permission grant is not proof that later automatic speech playback is unlocked. Check playback events and run a later asynchronous reply test before enabling hands-free.
2. Capture mono PCM through Web Audio/AudioWorklet. Read the actual capture/AudioContext sample rate; explicitly resample to **16,000 Hz**, rather than assuming a requested microphone sample rate was honored. Request echo cancellation/noise suppression for conversational capture, inspect actual settings and verify them acoustically. Do not require one MediaRecorder container/codec: raw PCM avoids codec decoding variability for ASR. If retaining a recording is enabled separately, feature-detect the recording format.
3. Vendor the **Silero VAD browser integration** and a matching pinned model/worklet/ORT set on the app origin. The current `ricky0123/vad` source supports legacy, v5 and v6 models; its v5/v6 ONNX files are each **2,327,524 bytes**, while legacy is **1,807,522 bytes**, from GitHub tree metadata. Use a tested matching version, not a silently updated CDN. The wrapper is ISC; Silero is MIT. These are artifact sizes, not runtime RAM. [Browser wrapper and assets](https://github.com/ricky0123/vad), [Silero source](https://github.com/snakers4/silero-vad).
4. Initial ASR footprint test: **`onnx-community/whisper-tiny`, `dtype: q8`, `device: wasm`, one WASM thread in a dedicated worker**, with `language: italian`, `task: transcribe`, bounded output, greedy decoding and no translation. Challenge tiny against **multilingual whisper-base q8** using the same recordings; base is the preferred quality candidate only if the whole voice loop meets the phone gate. Run a separate **fp16 WebGPU** trial under pinned Transformers.js **4.3.0** when `navigator.gpu` and `shader-f16` exist. Do not assume that the q8 WASM export is a supported or efficient WebGPU configuration. Validate exact model operators, output correctness and lifecycle on Safari. Keep small as a quality/stress candidate after tiny/base.
5. The baseline is utterance transcription after Stop or a detected pause; Whisper is not a genuine streaming recognizer. Optional overlapping chunk inference can supply clearly marked draft text, but costs more compute and can revise words. A visible transcript after every finalized utterance satisfies inspectable conversation history; an always-updating word-by-word transcript is a separate capability gate. Never claim that a text LLM or a batch ASR model provides it automatically.
6. Show raw recognized text as **what the app heard**, retain an edited/confirmed version separately, and send the actual learner turn once. Do not quietly repair the transcript before the teaching engine sees it. Save transcript/notes by default; keep bounded audio in memory and erase after use. Saved audio requires separate opt-in, as confirmed by the user.
7. Use the smallest passing local text tutor and one bounded reply generation with validation. Show the final approved reply as text before queuing its complete spoken output. Natural Italian recasts are the default correction style. On uncertain recognition or unsupported grammar judgement, ask a short Italian clarification; never penalize mastery or pronunciation from an uncertain ASR token.
8. Start with **half-duplex foreground turn taking**: listen → finalize/transcribe → think/validate → speak → listen again, without further taps after setup. Gate ASR and conversation VAD during TTS so the tutor cannot transcribe itself. Keep a single microphone stream for the active session if the exact-device trial supports this; gate consumption rather than repeatedly creating competing audio sessions. Stop tracks when the learner exits, pauses, switches profile or the page becomes hidden. On track mute/end, app suspension or route change, preserve the draft and display a clear paused state. Resume after an explicit tap where needed.

Suggested tunable pause settings are product choices, **not measurements**: roughly 0.8–1.2 seconds before finalization, a longer beginner/hesitation option, pre-roll to preserve the initial syllable, and bounded processing chunks below Whisper’s 30-second window. Chunk boundaries must not force the learner to stop: overlap, deduplicate and join longer explanations into the same conversational turn. Accept very short Italian answers such as *sì/no*; VAD minimum duration must not discard them. Offer manual Finish and Pause throughout.

## Verified model sizes and provider distinctions

Whisper’s code/weights are MIT; the multilingual tiny/base/small models have 39M/74M/244M parameters. **`.en` is English-only** and must not be chosen for Italian. Its published relative speeds are English/A100 results and do not predict iPhone latency. Italian is explicitly in its tokenizer’s language mapping. [OpenAI Whisper repository](https://github.com/openai/whisper), [language mapping](https://github.com/openai/whisper/blob/main/whisper/tokenizer.py).

The following are metadata sums for **only one encoder plus one merged decoder**, not every precision copy in the repository, not a transfer measurement, not a complete installed pack and not peak RAM:

| Multilingual ONNX export | q8 encoder + merged decoder | fp16 pair | q4 pair | Current revision observed |
| --- | ---: | ---: | ---: | --- |
| [whisper-tiny](https://huggingface.co/onnx-community/whisper-tiny/tree/main/onnx) | 40,844,231 B (40.8 MB) | 76,113,088 B (76.1 MB) | 95,734,369 B (95.7 MB) | `ff4177021cc41f7db950912b73ea4fdf7d01d8e7` |
| [whisper-base](https://huggingface.co/onnx-community/whisper-base/tree/main/onnx) | 76,894,629 B (76.9 MB) | 146,060,430 B (146.1 MB) | 142,374,870 B (142.4 MB) | `1846881b6b3a3024392c1eea3ad983695bc23925` |
| [whisper-small](https://huggingface.co/onnx-community/whisper-small/tree/main/onnx) | 249,077,005 B (249.1 MB) | 485,190,832 B (485.2 MB) | 299,331,431 B (299.3 MB) | `36050c46d777d46dc4b5f43f6d90574fc38f8732` |

q8 sums use `encoder_model_quantized.onnx` + `decoder_model_merged_quantized.onnx`; fp16/q4 use the matching suffix. Tokenizer, configs, JavaScript, workers and WASM are additional. Do not infer package size from “4-bit”: this tiny q4 decoder is larger than its q8 or fp16 equivalent. Pin complete manifests and verify hashes. HF trees/API metadata were read; the actual selected runtime fetch set and hashes still require inspection in the later prototype.

[Transformers.js 4.3.0 release](https://github.com/huggingface/transformers.js/releases/tag/4.3.0) specifically enables WebGPU for Safari 26+. This is stronger current evidence than older generic browser compatibility tables, but it is not a certification of Whisper fp16 or combined-model memory on iOS. [ORT provider documentation](https://onnxruntime.ai/docs/tutorials/web/) says WASM supports all ONNX operators, while GPU providers support a subset. [ORT settings](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html) require `crossOriginIsolated` for WASM multithreading; a worker keeps the UI responsive but does not itself accelerate inference. ORT’s proxy worker cannot be combined with its WebGPU provider; load the GPU runtime in a dedicated worker directly if that path works on the target. Prefer q8 for the CPU baseline; do not use fp16 CPU as the assumed faster configuration. [ORT performance guidance](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html).

GitHub Pages does not offer ordinary custom COOP/COEP response headers. Therefore the current host must not assume SharedArrayBuffer/pthread inference. Start with single-thread WASM and measured WebGPU. A hosting change is justified only if a measured need arises; do not insert a service-worker header shim into the offline shell without its own compatibility/offline tests.

**whisper.cpp is a separate engine/export lane**, useful particularly for native fallback. It supports native iOS, Metal, Core ML and a WASM browser example; Metal/Core ML support in native does not transfer to its browser WASM build. Its current README lists approximate memory of 273/388/852 MB for unquantized tiny/base/small; these are project estimates, not ONNX/Safari peaks. Quantized GGML Q5_1 artifacts are **32,152,673 / 59,707,625 / 190,085,487 bytes** in HF metadata. Its WASM example describes modern desktop CPU performance and SIMD, which must not be represented as phone results; threaded builds also need cross-origin isolation. [whisper.cpp](https://github.com/ggml-org/whisper.cpp), [WASM example](https://github.com/ggml-org/whisper.cpp/blob/master/examples/whisper.wasm/README.md), [GGML artifacts](https://huggingface.co/ggerganov/whisper.cpp/tree/main).

**sherpa-onnx** is Apache 2.0 and supports offline ASR, VAD and TTS on native iOS and WebAssembly; a Node addon is not a browser runtime. It can consolidate native speech components. Its model architecture support is not proof that every release asset is Italian or iPhone-ready. Use the explicit Whisper multilingual export or an explicit Italian model, and verify its model license separately. Streaming Italian-specific Zipformer/Kroko is a secondary candidate when continuous interim text becomes necessary; its separate export/license/runtime integration still needs scrutiny. [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx), [browser WASM build](https://k2-fsa.github.io/sherpa/onnx/wasm/index.html).

**Explicit Italian secondary ASR candidates:** the Kroko publisher distributes `Kroko-IT-Community-128-L-Streaming-001.data` at **155,836,193 bytes** and the 64-L variant at **155,839,229 bytes**, from its HF tree metadata. These are container artifacts, not proven direct Transformers.js ONNX inputs. Its model card distinguishes Apache-2.0 engine code from **CC-BY-SA community models**, advertises browser WASM, and still labels native iOS “coming soon.” Examine the exact LICENSE/archive/runtime rather than extrapolating from the sherpa engine’s platform list; no Italian learner benchmark or exact-phone result is given. [Publisher card and Italian artifacts](https://huggingface.co/Banafo/Kroko-ASR).

The LocalAI authors also publish Italian-tuned Whisper tiny/base/small with multiple read/conversational recipes, MIT models and GGML/CT2 exports. Their own Common Voice 25 Italian test reports tiny **27.1%** and base **19.2%** WER for the CV-only recipe, with different scores for multi-data versions. These are author reports on read speech, not the original generic Whisper models or learner conversation. The authors warn that small conversational-only variants can loop. No ready Transformers.js ONNX export is listed; native whisper.cpp is the simpler integration lane, or ONNX export/validation is extra prototype work. Treat these as quality challengers if generic tiny/base fail the Italian test, not demonstrated mobile winners. [Italian ASR authors, recipes and evaluations](https://github.com/localai-org/italian-asr), [base Italian multi GGML artifacts](https://huggingface.co/LocalAI-io/whisper-base-it-multi-ggml).

## Offline Italian speech output

**First choice: verified installed Italian system voice**, selected only when `localService === true`, with `lang` matching Italian, tested in airplane mode and from the installed PWA. A voice’s name or presence is insufficient. Wait for voice availability/`voiceschanged`; test start/end/error/watchdog recovery, queued bubbles, speaking speed, mute/replay, and repeated automatic playback. Local system TTS minimizes extra neural weights within the browser. The actual voice inventory/quality on the user’s phone remains unknown. [Web Speech specification](https://webaudio.github.io/web-speech-api/#dom-speechsynthesisvoice-localservice).

**Bundled alternative trial: sherpa-onnx VITS/Piper `it_IT-paola-medium`.** The model is explicitly Italian, one speaker, 22,050 Hz; the raw ONNX is about 63.5 MB. Its official sherpa archive is **67,221,173 bytes** from GitHub release metadata, before the separate WASM/JavaScript runtime. The pack includes tokens and eSpeak data, which must be provisioned too. The Piper repository card says MIT at repository level; this voice’s MODEL_CARD points to its Italian dataset, whose card declares **CC0-1.0**. Runtime/phonemizer licenses must be inventoried separately: sherpa code Apache 2.0, current OHF Piper engine GPL-3.0, eSpeak NG GPL-3.0. Preserve required notices/source distribution for the selected actual build rather than labeling the whole stack “MIT.” No Italian quality/latency result was measured. [Italian sherpa model and APIs](https://k2-fsa.github.io/sherpa/onnx/tts/all/Italian/vits-piper-it_IT-paola-medium.html), [Piper voice card/files](https://huggingface.co/rhasspy/piper-voices/tree/main/it/it_IT/paola/medium), [dataset card](https://huggingface.co/datasets/paolapersico1/Voice-Dataset-Italian), [current Piper engine](https://github.com/OHF-Voice/piper1-gpl), [eSpeak source](https://github.com/espeak-ng/espeak-ng).

**Kokoro is an alternative with an integration trap.** Kokoro-82M v1.0 weights are Apache 2.0 and have Italian `if_sara`/`im_nicola` voices. Its ONNX q8 file is **92,361,116 bytes** (model only), fp16 163,234,740 B and q4f16 154,586,422 B. However the current official `kokoro-js` voice table has its Italian entries **commented out**, while `phonemize.js` selects only `en-us` versus `en` and applies English normalization/postprocessing. Merely passing an Italian voice does not provide a supported Italian synthesis path and is rejected by its active voice validation. Use a verified Italian-aware phonemizer/integration, potentially sherpa, and evaluate accents, dates, numbers and clitics. [Kokoro model voices](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md), [ONNX files](https://huggingface.co/onnx-community/Kokoro-82M-v1.0-ONNX/tree/main/onnx), [actual JS voice table](https://github.com/hexgrad/kokoro/blob/main/kokoro.js/src/voices.js), [actual JS phonemizer](https://github.com/hexgrad/kokoro/blob/main/kokoro.js/src/phonemize.js), [voice validation](https://github.com/hexgrad/kokoro/blob/main/kokoro.js/src/kokoro.js).

Do not substitute attractive English-only speech releases. sherpa’s Pocket TTS release is labeled English; similarly inspect exact ASR/TTS releases rather than assuming a model family’s language coverage. The main plan covers newer Qwen ASR/TTS and direct-audio Gemma alternatives; Python/CUDA or native samples are not a PWA implementation.

## Safari local-recognition, gesture and microphone limits

Safari’s `webkitSpeechRecognition` is **not the offline/privacy guarantee**. WebKit originally described Siri-backed recognition, while the current maintained browser-compatibility data lists **Safari `SpeechRecognition.processLocally`, `.available()` and `.install()` as unsupported**. Assigning an unknown JavaScript property is not feature detection. Until Safari exposes and passes a local-only Italian capability/asset gate, do not use built-in recognition for the strict offline mode. [WebKit recognition announcement](https://webkit.org/blog/11648/new-webkit-features-in-safari-14-1/), [compatibility source](https://github.com/mdn/browser-compat-data/blob/main/api/SpeechRecognition.json), [local-recognition specification](https://webaudio.github.io/web-speech-api/#dom-speechrecognition-processlocally).

WebKit’s current source removes the iOS speech-start gesture restriction when `speak()` is called in a real gesture; later calls can then queue within that session. That supports an explicit Start plus audible welcome design, but does not guarantee that permission callbacks, restored sessions or every audio route will preserve it. Microphone permission alone is not an audio unlock. [SpeechSynthesis implementation](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/speech/SpeechSynthesis.cpp).

**Do not call the user’s iOS 26.6.1 known broken.** Open WebKit Bug 321436 initially reports SpeechRecognition stalling after media playback on one iPhone 12 Pro Max/iOS 26.6; a later reporter says their production app worked on 26.6.1 and broke on 27.0, with stuck synthesis queues/muted capture during Web Speech interactions. These are reporter reproductions, not our tests or a confirmed OS-wide condition. They justify exact-phone soak tests and watchdogs, especially because native recognition and playback can compete for an audio session. Our local PCM recognition avoids the built-in recognizer but still shares microphone/output platform resources. [Bug report](https://bugs.webkit.org/show_bug.cgi?id=321436).

Foreground hands-free is a credible trial scope. Background/locked-screen recording is outside the promised PWA scope; this is a conservative product boundary, not a claim that every current Safari configuration always forbids it. Suspend safely on visibility/lifecycle changes, phone calls, Siri, other capture, Bluetooth route changes and interruptions; handle `muted` even while `readyState` remains `live`. Screen Wake Lock, if available and user-enabled, may help a visible session but is not background execution permission. Request only audio under HTTPS with explicit permission and an obvious recording indicator/Stop control. The historical background issue below was resolved `CONFIGURATION CHANGED` for a WKWebView app with native background-audio configuration; later Add-to-Home-Screen behavior is reporter evidence. It cannot certify the current installed PWA. [Capture specification](https://w3c.github.io/mediacapture-main/), [WebKit microphone behavior](https://webkit.org/blog/7763/a-closer-look-into-webrtc/), [historical background microphone issue](https://bugs.webkit.org/show_bug.cgi?id=226620).

**True barge-in is a separate gate.** VAD identifies speech, not who produced it. Echo cancellation is a request/capability whose effective behavior must be tested with the actual speaker/headset, voice volume and room. The baseline disables conversation recognition during TTS. Optional hands-free learner interruption requires reliable echo-resistant VAD and bounded capture while output runs; on real learner speech, cancel playback once, capture the new turn and avoid replaying unheard speech automatically. Optional tutor interruption must wait for a stable clause/recognition and user-enabled preference, preserve the partial learner turn and give a brief Italian recast. Do not grade a transient partial hypothesis or repeatedly speak over a hesitant beginner. Provide tap-to-stop/manual input as the dependable interaction path while this optional capability is evaluated.

## Native fallback: exact local speech route

If speech fails the PWA quality, performance, offline playback or lifecycle gate even when the text tutor passes, the decision is still a **native app proposal**, not silently dropping spoken functionality. A native shell can preserve the web UI and bridge to Swift, but native code should own the microphone and playback rather than assuming WKWebView fixes browser capture.

Use **AVAudioEngine + SpeechAnalyzer + SpeechTranscriber or DictationTranscriber + SpeechDetector + AVSpeechSynthesizer**. Apple describes SpeechTranscriber as entirely on-device and suited to conversation; its language/device availability remains a runtime gate: `SpeechTranscriber.isAvailable`, `supportedLocale(equivalentTo: Locale(identifier: "it-IT"))`, `supportedLocales` and `installedLocales`. Do the equivalent **per-locale** checks for DictationTranscriber, without inventing a device-level `isAvailable` property for that class. Apple’s DictationTranscriber docs explicitly state it uses on-device dictation/SFSpeechRecognizer models and **does not support network-only locales**. Its `AnalysisContext.contextualStrings` can bias names/current lesson words, but bias must not be treated as proof the learner pronounced them. SpeechDetector works with a transcriber; tune/test its sensitivity because power-saving gating can drop short speech. [SpeechTranscriber](https://developer.apple.com/documentation/speech/speechtranscriber), [DictationTranscriber](https://developer.apple.com/documentation/speech/dictationtranscriber), [WWDC25 speech session](https://developer.apple.com/videos/play/wwdc2025/277/), [SpeechDetector](https://developer.apple.com/documentation/speech/speechdetector).

Apple’s **version-selected iOS 26** user guide explicitly lists Italian for Voice Memos transcription on iPhone 12+. The live feature-availability page lists Italian Italy/Switzerland for on-device/modeless Dictation but now labels **iOS/iPadOS 27**, so that live list is **not an iOS 26.6.1-specific compatibility guarantee**. These are useful evidence for an Italian native candidate, not substitute evidence that this API/device has the asset installed. Apple Intelligence Italian support is separate from Speech module locale support. [Voice Memos Italian guide, iOS 26](https://support.apple.com/it-it/guide/iphone/iph00953a982/26/ios/26), [current iOS feature availability](https://www.apple.com/ios/feature-availability/).

Use **AssetInventory** to reserve/check/download the Italian speech assets during explicit online provisioning, then verify installed readiness offline. Apple manages/shared assets outside the app package, may unsubscribe unused reservations and updates them; system management is not zero resource cost or a promise of eternal offline installation. Do not use opportunistic network retrieval during a conversation. [AssetInventory](https://developer.apple.com/documentation/speech/assetinventory).

AVSpeechSynthesizer supplies on-device speech; enumerate installed Italian voices, then test offline. Native AVAudioSession/AVAudioEngine voice processing offers echo cancellation. On supported recent hardware the alternative `setPrefersEchoCancelledInput` works only with the specified category/mode and must be checked via `isEchoCancelledInputAvailable/Enabled`; route changes can alter it. These controls improve the full-duplex trial; they do not prove perfect echo rejection or learner pronunciation accuracy. [Apple speech synthesis](https://developer.apple.com/documentation/avfoundation/speech-synthesis), [voice processing sample](https://developer.apple.com/documentation/avfaudio/using-voice-processing), [echo-cancelled input](https://developer.apple.com/documentation/avfaudio/avaudiosession/setprefersechocancelledinput(_:)).

If Apple’s Italian assets fail availability/recognition-quality gates, use multilingual whisper.cpp tiny/base Q5_1 with a measured Metal/Core ML build, or sherpa-onnx with an explicitly Italian supported model. The native text engine may use Apple Foundation Models when its own separate Italian/device readiness gate passes; the main plan owns that choice. Bridge calls/events should carry profile, conversation, turn and cancellation IDs; stale ASR/TTS results after profile/session changes cannot enter the active thread. PWA and wrapper storage migration remains explicit.

## Joint memory, latency and release test decision

Do not approve speech because ASR and the LLM each run separately. A browser model’s download size, native model RAM table, MLC catalog VRAM and the phone’s physical RAM are different quantities. Measure the installed PWA’s **combined resident ASR + text LLM + VAD + audio buffers + chosen TTS**, transient initialization and recovery. GPU work should be scheduled serially; co-residency still consumes memory while compute is idle. A one-time two-runtime load can duplicate WASM heaps or compilation assets. Do not let the optional existing 83 MB fit scorer load during the core feasibility trial unless it is an explicit integrated stress case.

The end-to-end response budget is **end-of-user-speech → pause decision → finalized ASR → accepted learner transcript → validated tutor reply → first audible Italian sample**. Record each segment, cold/warm p50/p95, full speech-generation time and queue underruns. Displaying unvalidated LLM tokens early does not meet the gate. Repeated unloading/reloading ASR or LLM may reduce resident memory but adds latency/heat; measure it as a fallback rather than assuming a benefit. A single 30-second 16 kHz Float32 buffer is 1.92 MB before copies/features; keep bounded queues and transfer buffers rather than retaining an hour of PCM.

Test after explicit installed-app provisioning: three force-close/airplane-mode reopens; manual record/stop/review/edit/send; consecutive hands-free exchanges without taps; saved transcript resume; errors and natural recasts; lookup and simplified Italian definitions; clean silence/no hallucinated transcript; hesitant A1 answers; fast C1/C2 clauses; learner accented Italian; noisy room; negation, clitics, numbers/names, *ho/o*, *è/e*; short *sì/no*; accents/diacritics; and whether recognizer “helpfully” normalizes the very mistake the tutor should discuss. ASR output alone is not pronunciation grading. Score Italian word error rate plus meaning-changing errors and a separate false-correction rubric reviewed by Italian educators.

Run a 30–60 minute combined-model soak with speaker and headset routes, temperature/battery tracking, repeated TTS/listen transitions, app switch/lock/call interruption/resume and cancellation/profile change. Revisit at least 100 stored turns without retaining their raw PCM. Test storage eviction/partial pack repair and verify no learner audio/text is sent anywhere; model downloads occur only in explicit provisioning. Until these pass, mark offline speech **candidate/unverified**, while existing written modes remain available as reduced functionality. If tiny/base cannot meet Italian recognition and complete-loop gates, or a local system/Piper voice cannot sustain offline automatic playback, present a concrete native plan for the full feature.


## Product decision and confirmed defaults

The [combined plan](../../PLAN-UNIFIED-LEARNING-OFFLINE-AI-2026-10-03.md) governs product and release gates. Defaults confirmed by the user are natural spoken correction followed by continued conversation, saved transcripts and learning notes, and audio saved only when explicitly chosen. The pause intervals above are trial settings, not locked behavior or measured latency. Long explanations remain supported through chunking. A native route is a proposal requiring a distribution decision, not an automatic migration.
